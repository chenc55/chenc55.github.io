03 / 桌面工具 · 二次开发

微语 / WXtool

一项基于 WechatVibe 二次开发的 Windows 桌面应用实践，将会话统计、原文回看与可选分析组织在同一工作台中。

基于 WechatVibe 二次开发

项目简介问题与思路操作演示界面与功能实现原理技术栈项目思考

01 / 项目简介

从聊天回顾出发，连接桌面交互与数据分析。

这项实践从回看聊天时的两个需求展开：快速了解一段交流的规模与节奏，以及找到具体消息并读到上下文。连续的聊天气泡不便于概览，单条搜索结果又容易失去语境，因此工作台把消息统计与原文入口放在一起。

项目基于 WechatVibe 二次开发，在上游聊天读取与分析能力之上整理会话概览和快捷入口。这里重点展示桌面界面、本机服务与分析任务如何衔接，以及如何区分可核对的统计和需要审慎理解的模型判断。

应用场景

Windows 上的个人聊天回顾场景：浏览有权访问的会话、查找原文、了解已加载消息的交流节奏。

实践内容

  • 会话概览与消息统计
  • 关键词搜索与原文定位
  • 分析任务状态与账号隔离

02 / 问题与思路

从具体问题，梳理实现思路。

01

记录很多，缺少概览

遇到的问题
只看连续的聊天气泡，很难快速了解这一段交流的规模和节奏。
实现思路
以已加载消息为明确范围，汇总数量、类型、平均文本长度、发言占比和小时分布，形成会话概览。
02

找到一句话，仍缺上下文

遇到的问题
搜到关键词后，孤立的句子可能不足以理解当时讨论的事情。
实现思路
把关键词或日期搜索与原文定位连接起来，搜索结果可以继续展开前后消息。
03

统计与推测容易混在一起

遇到的问题
消息数量与情绪、意图等模型判断性质不同，需要分别理解。
实现思路
让工作台统计独立于模型运行，分析另设入口，并用进度与待分析状态说明当前任务情况。

04 / 实现原理

一次操作，背后如何流转。

先限定样本，再解释数字

统计只处理已加载消息。未知发送者单独计数，无效时间不进入时段图；群聊将其他成员合并显示，避免把局部样本包装成完整关系结论。

桌面交互与分析分工

Electron 承载界面，Python 处理本机数据和任务，Node 负责模型调用。界面通过本机 HTTP 读取状态，模型计算不直接塞进页面交互代码。

切换账号也切换上下文

SQLite 文件按账号区分，历史游标校验账号与会话；前端在账号变化时取消旧请求并重置当前视图，减少旧结果串入新会话的风险。

05 / 技术栈

每一层技术，都有具体职责。

从各项技术的具体用法，到它们如何配合完成一次操作。

桌面容器
  • Electron

将本机工作台装入 Windows 桌面窗口，并衔接服务启动、窗口状态与受限桌面接口。

  • Electron：窗口与页面的连接

    主进程创建应用窗口并加载本机服务地址，预加载脚本通过明确的接口传递桌面事件。窗口开启上下文隔离并关闭页面的 Node 集成，使工作台通过约定接口与桌面容器协作。

如何配合

启动时先等待 Python 服务返回本机地址，确认服务就绪后再由 Electron 加载工作台。

沟通工作台
  • HTML
  • CSS
  • JavaScript

主工作台使用网页结构、样式与交互代码，连接会话选择、事实统计、原文回看和任务状态。

  • HTML 与 CSS：组织信息与阅读顺序

    HTML 定义会话选择、统计卡片和聊天入口，CSS 负责主题颜色、网格布局及窄窗口下的排列调整。消息数量、交流时段和模型状态分别呈现，让原始统计与待分析内容保持清楚的视觉层次。

  • JavaScript：计算统计并同步视图

    统计函数先按消息标识去重，再汇总类型、文本长度、小时分布和发言比例，只处理已加载窗口且不调用模型。交互代码处理会话选择与请求状态，账号变化时取消旧请求并重置历史位置。

如何配合

选中会话后，页面取得消息窗口，计算统计并更新图表；查看原文与发起分析仍是分别触发的操作。

本机服务
  • Python
  • HTTP

在桌面页面与数据、模型进程之间组织请求，处理账号上下文、消息窗口、历史查询与任务状态。

  • Python：组织带上下文的数据读取

    桥接代码将会话、消息和分析状态整理成页面可读取的数据，并处理历史分页与关键词、日期查询。历史游标携带账号、会话及消息位置，读取下一页时核对这些条件，避免沿用不属于当前会话的位置。

  • HTTP：提供本机页面接口

    服务监听回环地址，页面通过 HTTP 请求读取消息、查询历史或获取任务状态，响应以 JSON 为主。请求入口核对 Host 与 Origin；这说明本机接口的访问约束，不表示后续远程模型调用也在离线环境中完成。

如何配合

页面提交关键词和会话信息后，Python 查询历史并返回定位信息，前端据此展示原文及前后消息。

分析执行
  • Node.js
  • TypeScript
  • ONNX Runtime

将模型调用放在独立于页面交互的执行路径中，按来源运行本地 Laya 或调用配置的 API。

  • Node.js 与 TypeScript：传递模型任务

    Python 启动 Node 子进程，通过带编号的 JSON 消息发送任务并接收结果；TypeScript 描述模型配置、请求及返回结构。API 连接器校验协议与配置，远程分析和聊天助手会将相关上下文发送至配置的服务。

  • ONNX Runtime：执行本地 Laya 模型

    本地执行器加载 ONNX 模型文件，把整理后的输入转换为张量并运行推理，再将输出交给分析逻辑解释。自动模式在 Windows 尝试 WebGPU，并具备转用 CPU 的路径，让同一分析入口能衔接不同执行后端。

如何配合

发起分析后，桥接层发送模型任务并接收带编号的结果，再将状态和分析内容提供给工作台。

本地持久化
  • SQLite

使用本地数据库保存会话选择、分析结果与任务进度，供后续读取和继续处理。

  • SQLite：保存有归属的状态与结果

    数据库文件按账号区分，会话选择和分析结果使用独立表；结果记录还包含会话、版本或模型来源，便于按对应范围读取。进度表保存已处理位置与批次状态，将可继续处理的进度与已完成的结果分别记录。

如何配合

再次查看某个会话时，服务按当前账号和模型来源读取已存结果，前端据此呈现已有内容及任务状态。

06 / 项目思考

实现过程中的选择与思考。

本地能力与 API 各有边界

这项实践需要说明不同分析路径的数据去向：事实统计和本地 Laya 可在本机处理，远程 API 分析与聊天助手则会发送相关上下文给所配置的服务。整个工具不能概括为全程离线，模型推测也不能替代对原文的判断。

展示操作，不替代真实验收

图片与视频使用合成聊天，视频未连接模型。这些材料用于说明工作台、搜索和统计的实现，分析准确度与不同微信版本的兼容性仍需在相应环境中验证。
