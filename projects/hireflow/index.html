02 / AI 应用 · 招聘协作

青衿 / HireFlow

围绕简历筛选展开的全栈与 AI 应用实践，重点是材料管理、评估依据和角色协作。

项目简介问题与思路操作演示界面与功能实现原理技术栈项目思考

01 / 项目简介

从简历材料到人工决定，梳理一条有据可查的流程。

这个项目从招聘筛选中的信息衔接问题出发：岗位要求、简历原文和处理进度分散时，材料归属、评分理由与交接记录很容易脱节。因此，青衿以岗位为主线组织材料、评估和人工处理。

这段实践关注的是如何把 AI 建议放进可核对的业务流程。模型生成逐项评价，服务端回查证据，HR 核对后回传，招聘负责人再记录决定；界面、后台任务与历史版本围绕这条流程衔接。

应用场景

面向需要按岗位整理简历、协同筛选与记录用人决定的 HR 和招聘负责人。

实践内容

  • 岗位与材料的状态管理
  • 逐项评估与原文证据核验
  • HR 与招聘负责人的协作流程

02 / 问题与思路

从具体问题，梳理实现思路。

01

材料归属与状态容易混乱

遇到的问题
多岗位同时收简历，重复上传、草稿和已提交材料容易混在一起。
实现思路
上传时绑定岗位，按状态查看投递；同一 HR、同一岗位的相同文件做去重。
02

一个总分难以解释推荐理由

遇到的问题
只看分数，无法知道哪些要求得到证明、哪些信息仍需核实。
实现思路
把岗位要求拆成逐项评价，附理由与原文引用，再按已发布权重汇总。
03

协作交接缺少明确界限

遇到的问题
初步评分与最终录用决定混在一起，难以追溯是谁做了什么判断。
实现思路
HR 核对并回传报告；老板查看已回传结果，另行记录录用、不录用或暂缓。

04 / 实现原理

一次操作，背后如何流转。

模型评价，程序核算

服务端按文件哈希、文本块和字符区间重新核验引文。当前规则下，无有效证据记 0 分，部分匹配按证据给分；旧区间报告单独保留。

报告绑定输入版本

评分绑定岗位要求、简历版本和运行配置快照；历史详情按评估编号读取。人工意见另行追加，便于对照判断而不改写原报告。

长任务交给独立 Worker

解析和评分写入持久化队列，网页无需等待模型完成。并发处理使用独立数据库会话，并以领取租约和心跳检查任务归属。

05 / 技术栈

每一层技术，都有具体职责。

从各项技术的具体用法，到它们如何配合完成一次操作。

交互界面
  • React 19
  • TypeScript
  • Vite
  • TanStack Query

将岗位、材料与报告串成操作流程，管理请求状态、历史切换和刷新反馈。

  • React 19 与 TypeScript

    React 将岗位列表、筛选条件和评估详情组织成组件，页面根据选择和请求结果更新。TypeScript 为接口数据与组件参数提供类型约束，帮助区分投递、简历版本和评估编号。

  • Vite

    开发时提供页面服务，并把接口请求转发给后端；构建时先执行 TypeScript 检查，再生成静态资源。这样可以分别处理页面开发与业务服务运行，构建产物交给 Nginx 提供访问。

  • TanStack Query

    以岗位、分页条件或评估编号组成查询标识，分别管理数据、加载和失败状态。回传材料或追加意见后刷新相关查询，使操作反馈与服务端记录衔接，而不是只修改页面上的数字。

如何配合

查看历史报告时，页面按选中的评估编号请求详情，再读取对应简历版本，避免用最新结果替换正在查看的历史记录。

业务接口
  • Python
  • FastAPI
  • Pydantic

将请求校验、对象权限与角色操作规则落实到接口，衔接 HR 核对和负责人决策。

  • Python 与 FastAPI

    Python 承载材料、评分和协作业务，FastAPI 将岗位、投递、报告等能力组织成 HTTP 路由。接口取得当前用户与数据库会话后再进入业务处理，权限判断不只依赖页面是否显示按钮。

  • Pydantic

    用数据模型校验请求和领域对象，约束编号、分值、权重及时间格式，并拒绝未知字段。岗位要求发布时还检查启用项权重总和，避免把结构不完整的数据直接送入后续评分流程。

如何配合

HR 提交材料时，接口核对岗位权限、简历版本和解析状态，再创建评分任务；负责人记录决定则走独立的人工意见流程。

数据与任务
  • PostgreSQL
  • SQLAlchemy
  • Alembic

保存输入版本、历史报告和持久化任务状态，通过迁移维护数据库结构。

  • PostgreSQL 与 SQLAlchemy

    PostgreSQL 保存岗位、简历版本、评估与任务记录；SQLAlchemy 将这些表映射为对象并管理数据库会话。Worker 领取任务时结合行锁、租约和心跳检查归属，各并发槽使用独立会话。

  • Alembic

    用有顺序的迁移脚本记录表与索引的变化，例如为 HR 回传记录建立独立表。应用数据模型与结构演进分开维护，便于核对某个业务能力依赖哪些数据库变更。

如何配合

API 写入持久化任务后，独立 Worker 领取并处理，将状态与评估结果写回数据库，前端随后通过接口读取进度和报告。

PDF 与模型
  • PyMuPDF
  • DeepSeek API

从 PDF 提取可定位文本，接入逐项评价并保留引文核验所需信息；演示使用预设 Mock。

  • PyMuPDF

    从 PDF 提取页面与文本块，再由解析流程保留页码、原文、坐标和字符映射，供报告回查引用。扫描页或文本质量不足会被标记，不能把未提取到的内容直接当作候选人不具备某项经历。

  • DeepSeek API

    接收岗位要求和处理后的材料，返回逐项评价与引文，再由程序校验输出、回查原文并汇总分数。模型调用失败不会自动改用 Mock；展厅演示单独采用预设结果，引文对应也不证明经历真实。

如何配合

解析层提供可定位的文本块，模型给出评价建议，证据校验层再检查引用是否对应原文，最终报告交由 HR 核对。

部署组织
  • Docker Compose
  • Nginx

分离前端、API、Worker 和数据库的运行职责。

  • Docker Compose

    配置中将数据库、API、Worker 和前端拆为不同服务，声明依赖检查及存储卷。长时间的解析和模型调用由 Worker 执行，页面与 API 不承担同一进程内的所有职责。

  • Nginx

    提供构建后的前端文件，将同一站点下的 API 请求转发给内部后端，并在部署配置中承担 TLS 入口。浏览器使用统一入口访问页面和业务接口；配置存在不代表当前已公网部署。

如何配合

浏览器先访问 Nginx，业务请求再到 FastAPI；API 与 Worker 通过数据库任务衔接，各服务按部署配置分别运行。

06 / 项目思考

实现过程中的选择与思考。

明确模型建议的边界

这段实践把来源核验和业务判断分开：引文可回查只说明来源对应，不证明经历真实或岗位适配。扫描页、文本质量不足及最终用人决定仍交由人工处理。

演示流程与实际效果分开

图像和视频使用合成材料及预设结果，展示操作与信息结构，不代表真实招聘准确率、上线状态或效率提升。
